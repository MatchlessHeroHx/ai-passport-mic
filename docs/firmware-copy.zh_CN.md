# Passport Mic 固件文案优化清单（体验精修版）

本清单针对桌面听写硬件 Passport Mic 进行全场景体验校对。
优化核心原则：
1. **去 AI 虚伪感与过度拟人**：剔除“说得真好”、“文化/有话，尽管说”、“闹脾气”等容易让严肃办公出戏的伪情感表达。
2. **拒绝冰冷工业腔**：不用“音频采样受阻”、“已递送”等生硬工程词，保持轻盈、温和、克制的伴侣感。
3. **适配物理尺寸与视线动线**：严格遵守硬件单句宽度（不超过 12 个汉字），操作键与动作之间加入分隔符，杜绝语义歧义。

## 一、底部卡片核心交互文案

| 状态 | 区域 | 原文案 | 优化文案 | 场景化校对与优化依据 |
| :--- | :--- | :--- | :--- | :--- |
| **就绪** | 标题行 | 有话，尽管说 | **随时在听** | 原句是典型的生硬 AI 翻译腔（Speak your mind / Have something to say），带逗号且带有教导感。“随时在听”克制温和，传达随取随用的常驻状态。 |
|  | 说明行 | 上 撤销 · 下 发送 | **上 撤回 · 下 发送** | 桌面打字/IM 语境中，“撤回”比“撤销”更符合输入体验；保持中点对齐。 |
|  | 提示行 | 确定  开始说话 | **按确定 · 开始说话** | 原文用两个空格隔开，极易被读成“确定要开始说话”；加入“按”与中点，指引明确。 |
| **未连接** | 标题行 | 等你连接 | **等待连接** | 去除干瘪的被动态表达，恢复标准且干净的设备状态。 |
|  | 说明行 | 打开 Mac 上的桥接程序 | **在 Mac 打开 Passport** | 普通用户无法理解何为“桥接程序”（Bridge）；直接提示打开对应 Mac 应用名。 |
|  | 提示行 | （空） | **（保持空）** | 未连接时不给多余操作干扰。 |
| **配对中** | 标题行 | 六位配对码（如 `123456`） | **六位配对码** | 保持数字展示。 |
|  | 说明行 | 在 Mac 上输入这串数字 | **请在 Mac 输入配对码** | 比“这串数字”更具产品规范感。 |
|  | 提示行 | 等待蓝牙配对 | **等待确认中…** | 用户视线已移至电脑，提示语保持轻量等待感知。 |
| **启动中** | 标题行 | 准备好了吗 | **正在准备…** | 用户按下按键后希望设备迅速就绪，反问“准备好了吗”像在推卸设备延迟责任。 |
|  | 说明行 | 正在打开 Mac 听写 | **正在开启听写** | 去掉不必要的“Mac”字样，表意更利落。 |
|  | 提示行 | 马上就好 | **稍候** | 简明干脆，避免 2 秒卡顿时的无力安慰感。 |
| **录音中** | 标题行 | 计时，如 `00:42` | **计时不变** | 保留。 |
|  | 说明行 | （波形动画） | （波形动画） | 保留。 |
|  | 提示行 | 说完按确定 | **说完按确定** | 已经足够自然，予以保留。 |
| **刚录完** | 标题行 | 录音时长 | **时长不变** | 保留。 |
|  | 说明行 | 这段已经交给 Mac 了 | **内容已同步到 Mac** | 原文“交给 Mac 了”口语过于随意；“已同步到 Mac”给用户清晰的确定感与安全感。 |
|  | 提示行 | 确定  再说一段 | **按确定 · 继续说** | 解决空格歧义，且“继续说”比“再说一段”更符合连贯创作场景。 |
| **刚撤销** | 说明行 | 已发送撤销 | **已撤回** | 消除“发送撤销”这种程序事件日志写法，直接给结果。 |
| **刚发送** | 说明行 | 已发送回车 | **已发送** | 还原用户在打字/通讯软件里的核心目的（发送），而非机械地说明按了回车键。 |
| **麦克风出错** | 标题行 | 麦克风出错了 | **麦克风暂不可用** | 原文一屏出现三次“出错”，改成客观中立的状态说明。 |
|  | 说明行 | 请重启设备 | **长按电源键重启** | 给出确切的操作方式，降低故障时的排查门槛。 |
|  | 提示行 | 重启后再试 | **重启后自动连接** | 告知预期结果，消除焦虑。 |

## 三、肩部气泡短句（场景化精修）

> **设计基调**：桌面上的陪伴型话筒，应是“安静的倾听者”，而不是“聒噪的话痨”或“谄媚的 AI”。字数均控制在 12 汉字以内。

### 1. 待机就绪（每 9 秒自动轮换）
*使用场景：用户正在看屏幕思考、构思文字、阅读网页或沉浸工作。气泡应当安静、不争宠。*

| 原文案 | 优化后文案 | 场景校对理由 |
| :--- | :--- | :--- |
| 有话，尽管说 | **随时可以说** | 删去命令式的“尽管”，语气温润。 |
| 按确定，我就开始听 | **按确定，随时在听** | 减少机械的条件从句感。 |
| 想说什么都可以 | **有想法，随时开口** | 贴合创意、灵感记录场景。 |
| 我在这儿呢 | **随时都在** | 去除稍显腻歪的语气词，更具陪伴感。 |
| 慢慢想，不着急 | **慢慢想，不着急** | （保留）节奏温和，适合创作者沉思。 |
| 今天过得怎么样？ | **今天还顺心吗？** | 比客服式的“过得怎么样”更真诚一点。 |
| 需要我帮你记吗？ | **随时为你记录** | 陈述随时待命，不反问打扰。 |
| 说一句试试？ | **轻按一下，就能说** | 原文像软件自测提示，修改后提供明确的行为引导。 |

### 2. 刚连上那一刻
*使用场景：设备刚刚连上 Mac 客户端，给用户一个安心的上线反馈。*

| 原文案 | 优化后文案 | 场景校对理由 |
| :--- | :--- | :--- |
| 连上啦 | **已连接好** | 利落踏实。 |
| 嗨，又见面了 | **嗨，又见面了** | （保留）适合熟练老用户的亲切感。 |
| 我准备好了 | **已准备就绪** | 干净清爽。 |
| 今天想说点什么？ | **今天想聊些什么？** | 自然口语，去掉刻意的发问感。 |

### 3. 倾听中（录音前 60 秒）
*使用场景：用户正在专注说话，视线余光看到硬件，需要确认“它确实听进去了”，但绝不能抢戏。*

| 原文案 | 优化后文案 | 场景校对理由 |
| :--- | :--- | :--- |
| 嗯…… | **细心听着** | **重点修改！** 屏幕上显示“嗯……”极易让用户误以为设备卡顿或是在敷衍。 |
| 嗯嗯，你说 | **请说，我在听** | 消除“嗯嗯”的客服随声附和感，更专注。 |
| 我在听 | **我在听** | （保留）经典、安心。 |
| 继续，我记着呢 | **继续说，都记着** | 去除啰嗦代词，表达紧凑。 |
| 慢慢说 | **不急，慢慢说** | 给予表达节奏上的从容感。 |
| 听着呢 | **听着呢** | （保留）地道自然的收音反馈。 |

### 4. 说了很久（录音超过 60 秒）
*使用场景：用户一口气说了很长一段，可能在理清逻辑，也可能是长时间汇报。此时切忌催促或抱怨。*

| 原文案 | 优化后文案 | 场景校对理由 |
| :--- | :--- | :--- |
| 说了好久啦 | **别着急，慢慢讲** | 原文“说了好久啦”潜意识在抱怨用户说太多；优化后安抚用户继续表达。 |
| 累了就歇一下 | **长语音记录中…** | 严肃工作场景下蹦出“累了就歇一下”容易让人生烦，转为客观展示其长续航收音能力。 |
| 我都记着呢 | **都在完整记录** | 给予可靠、稳定的技术信任感。 |
| 说完按确定就好 | **说完按一下确定** | 顺手自然的结束提示。 |

### 5. 刚录完与提交
*使用场景：用户刚刚按键结束说话，可能是工作邮件、代码注释、闲聊甚至牢骚，文案必须保持客观包容。*

| 原文案 | 优化后文案 | 场景校对理由 |
| :--- | :--- | :--- |
| 说得真好 | **这段录好了** | **必须删除原文！** 用户如果是在骂人、报故障、录丧气话，看到“说得真好”是灾难级体验。 |
| 都交给 Mac 了 | **已同步完成** | 明确的结果反馈。 |
| 好嘞 | **收到** | 干脆利落，去除浮躁感。 |
| 收到啦 | **都记好了** | 踏实可靠。 |
| 记下了 | **记下了** | （保留）短小有力。 |
| 这段我听清了 | **这段听清了** | 省去多余人称，更符合中文口语习惯。 |

### 6. 发送与撤销
*使用场景：用户按了上键或下键，属于快速高频的功能性操作，反馈必须秒懂。*

| 原文案 | 优化后文案 | 场景校对理由 |
| :--- | :--- | :--- |
| 嗖，送达 | **已发送** | 去掉“嗖”这种幼齿化拟声词，符合成年人桌面设备的格调。 |
| 好，发送 | **发送完成** | 动作闭环感。 |
| 发出去啦 | **已发出** | 利落。 |
| 已经发走了 | **已送达** | 精准。 |
| 当我没听见 | **刚才的不算** | 原文略带耍小聪明的戏谑感，优化后更像贴心同伴的配合。 |
| 没事，重来 | **没关系，重来一次** | 宽容柔和。 |
| 撤回啦 | **已撤回** | 消除叠词卖萌感。 |
| 删掉了 | **已抹除** | 明确彻底。 |

### 7. 未连接与配对中
*使用场景：用户刚开机或连接中断，急于配对连上电脑，文案要高效指引，不要消极摆烂。*

| 原文案 | 优化后文案 | 场景校对理由 |
| :--- | :--- | :--- |
| 我先发会儿呆 | **正在静候连接** | 设备不应向用户传递“我在摸鱼/发呆”的印象。 |
| 等你来找我 | **等待设备接入** | 规范清晰。 |
| 在等你的 Mac 哦 | **等待 Mac 连接** | 去除句尾“哦”，端正专业。 |
| 桥接程序开了吗？ | **Mac 客户端已打开吗？** | 直指用户电脑上的实际 App。 |
| Mac 那边还没动静 | **暂未检测到 Mac** | 客观陈述技术状态。 |
| 第一次见面，认识一下 | **正在等待配对确认** | 配对时用户注意力在敲键盘，简洁直白更重要。 |
| 配对一下吧 | **请在 Mac 确认配对** | 具备明确的行为引导力。 |
| 在 Mac 输入这串数字 | **请在电脑输入配对码** | 统一术语为“配对码”。 |

### 8. 麦克风出错（故障态）
*使用场景：硬件异常，用户情绪处于不耐烦边缘。必须真诚、专业，严禁嬉皮笑脸。*

| 原文案 | 优化后文案 | 场景校对理由 |
| :--- | :--- | :--- |
| 麦克风闹脾气了 | **麦克风启动异常** | 绝对不要在硬件故障时卖萌撒娇（“闹脾气”会极大激怒遇到问题的用户）。 |
| 我好像听不见了 | **未采集到声音信号** | 清晰指出具体问题。 |
| 重启一下我吧 | **请长按重启设备** | 提供立即可行的解决方案。 |

## 四、固件开发与落地建议

1. **解决短句同屏重复问题**：
   - 当就绪标题为“随时在听”时，气泡中不要同时刷出“随时在听”，建议在 `mic_lines.c` 的就绪词库中剔除与标题同构的句子。
2. **字符宽度与字库重新生成**：
   - 优化后的文案单句最大长度为 9 个汉字（如“Mac 客户端已打开吗？”），完全在原屏幕单句上限 196 像素（约 12 个汉字）的安全范围内。
   - 更新文案后需重新抽取汉字字形补入字库。

## 五、落地时按硬件做的调整

以下两处已与负责人确认，固件按右列实现，其余文案与上文一致：

| 位置 | 优化稿 | 固件实际 | 原因 |
| :--- | :--- | :--- | :--- |
| 麦克风出错 · 说明行 | 长按电源键重启 | 长按电源键关机 | 电源键长按约 2 秒是关机，不会自动开机 |
| 麦克风出错 · 提示行 | 重启后自动连接 | 再长按开机 | 同上，需要用户再按住 0.5 秒开机 |
| 麦克风出错 · 气泡 | 请长按重启设备 | 请关机后重新开机 | 同上 |
| 未连接 · 说明行 | 在 Mac 打开 Passport | 在 Mac 打开 Passport Mic | 和 Mac 菜单栏、蓝牙里的名字一致 |
| 未连接 · 气泡 | Mac 客户端已打开吗？ | Passport Mic 已打开吗？ | 同上 |

另外两处行为同步修正：「刚连上」的气泡现在会完整显示约 4 秒，不再被待机句子立即替换；气泡挑句时会跳过与当前标题或说明行相同的句子。
